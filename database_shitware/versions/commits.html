fe71eea - x3hy, 10 days ago
the way the authentication function works is that it requests to see if
the current user has ring-2 access, in order to have ring-2 access the
user must have not only passed ring-1 but also they must be a valid
administrative user.

The old validate_session_permanence function would ping the server to
check if the user had ring-1 access then it would ping the server again
to check for ring-2 access.

You might have already caught the optimisation I missed. We send two
requests in which the second one (ring-2 check) REQUIRES ring-1, and we
already check ring-1 before checking ring-2.

This means we are sending two requests to the server for nearly the same
information, we know that if the second request passes (ring-2) then the
first request must also have passed (because again ring-2 access
requires ring-1 access also).

I changed my function to instead query for ring-2 access first, this way
if the ring-2 access passed then we know that the user has valid ring-1
credentials. If the ring-2 request fails then the user is either invalid
or not a user, in this case we send a second request querying for ring-1
access, if this OPTIONAL SECONDARY CALL fails then we know the user has
neither ring-1 nor ring-2 access, simularily if the second call passes
then we know the user has ring-1 access, just not ring-2.

Now the new function with this two-step authentication is below:

1  // if a user is not signed in then they will be
2  // sent to the sign-in page. callback is run if user
3  // is not signed in.
4  async function validate_session_permanence(callback){
5  	function _callback(){
6  		sign_out();
7  		open_error("You are not signed in.", 202);
8  	}
9
10 	// check ring 2 access first, if this passes then
11 	// we know the user must have valid id to pass ring 1.
12 	//
13 	// if we simply checked the validity using the regular
14 	// auth call then we'd also have to figure out if the
15 	// user was an admin, this function kills two auths with
16 	// one request.
17 	if (await update_admin_status() == false)
18 		if (await update_session() == false)
19 			if (callback == undefined)
20 				_callback();
21 			else callback();
22 	else _is_valid = true;
23 	init_auth_elements();
24 	_is_loaded = true;
25 }

As you can see on lines 17 and 18 we call functions that (assumed) will
fetch the admin status and the validity of the user (respectfully).
These calls are then compared to false to check if they failed or not.

the old function did the following:

17 	if (!await update_admin_status())
18 		if (!await update_session())

This failed because await has some strange behavior causing it to
compare the output of an unresolved Promise. This issue ended up causing
the function to pass the conditional before it had finished reading the
response from the server. This meant that regardless of admin status,
the function would ALWAYS send two requests (unless you had an edge case
of perfectly instant internet and processing speed).

authentication. On session validation the frontend checks that the user

user is an admin and if they are currently logged in. This means that if
a feature requests to see if the user is an admin instead of prompting
the server we can just use the cached value and get the server response
once. Another system I improved was the validate_session_permanence

else it will throw them off the page (required sign-in pages like the

admin. this means two requests for authentication of an admin, and two
requests every time the old system would query for the users validity.

Back to "Removed all traces of sessions". I've decided to remove my
implementation of sessions (with a table and auto-regenerating ids)
because this would take too much time to implement. Instead I've decided
to use a basic authentication header. This means that for every request
to the server, a users username and password needs to be provided. This
is fundamentally unsecure as a potential hacker could intercept the
packet and gain access to any user-(permission)-level calls. In a real
project this system would be replaced with an auto-regenerating session,
so instead of a username and password given a session token is given.
On every request (to the server) the token is re-generated.

  same thing in the front end. What I mean by this is that if i was to

  enter their username and password to sign in. Obviously I'd need HTML
  builtin form validation through the input field parameters such as
  `minlength`, `maxlength`, `type` and so on. This is not enough of course
  so I'd need some front-end checking outside of the HTML parameters
  that will confirm the data is secure. Then finally the server has to
  validate the data once more to confirm the sent data was not compromised
  or faked.

  This means we have three separate validations all of which need to be
  implemented in different languages (HTML for the front-end, JavaScript
  for the client-side back-end and finally PHP for the server-side
  back-end).

  If instead I had a file that acted as a API to send in text and have it
  run a function on the SERVER then boom it can be validated with only a
  server-side check. Also if the main checking functions are server-side
  they can be reused to validate the data when its sent in! This means
  with just one set of functions you could theoretically validate and
  verify the data before and when its being sent to the server!

  request-management code. The method of request management I'm going to

  connection to the database, it also contains a bunch of functions that
  require a database connection, these functions are used through the
  other files.
- post_library.php - This file is what you use to safely include the
  library file. This file manages the dependancies, eg I was having this
  brief issue where the library.php file would be loaded twice, this was
  resolved by adding a simple C-style header block at the top of the
  post_library.php file which makes it so that the library.php file and
  any other dependancies can only be included ONCE. All other requests are
  blocked. This file also checks to ensure that all the defined tables
  exist, if for some reason a table is missing from the database that is
  required, the post_library.php file will echo the error messages and
  then run the db_reset.php file on its own which will reset the database
  back to its defaults. This is very useful for if something really bad
  goes wrong, the next time someone opens the page the website will
  automatically reset the database and fix any potential outages. I
  understand that this might be bad in the fact that if people broke the
  database and had no backups of the data then it would be automatically
  lost forever, but to argue that I say, why in tarnation would a table
  disapear from the db unless some critical issues was happening, perhaps
  this issue was a hacker that has gained access to the db? I don't plan
  on allowing even admins the access to delete tables so if for some
  reason a hacker/attacker has attacked the db, and they decide to delete
  a table, the rest of the data will be destroyed.. Hows that for
  security.. A dead-mans switch if you will.
